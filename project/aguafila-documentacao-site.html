01
Sobre o Produto

O que é o AguaFila?

O AguaFila digitaliza a fila de atendimento de distribuidoras de água que carregam caminhões e veículos com galões — substituindo a fila física informal por três telas conectadas em tempo real, funcionando inteiramente na rede local do pátio, sem depender de internet.

⚠️
O Problema
Filas físicas informais geram disputas sobre a ordem de chegada, esteiras de carregamento ociosas por falta de coordenação, nenhum histórico de atendimentos e uma experiência pouco profissional para o motorista.
💧
A Solução
Três telas conectadas por WebSocket: o motorista retira uma senha no Terminal, o operador chama e finaliza atendimentos, e o Painel Público anuncia por voz — tudo instantâneo, tudo na rede do próprio pátio.
🎯
Estado Atual
MVP funcional cobrindo o ciclo completo — emissão, fila, chamada, atendimento e finalização — com persistência real em banco relacional. Autenticação, relatórios e múltiplos operadores estão no roadmap.

Proposta de Valor

  • ✓
    Zero-dependência de internet — roda 100% em rede local (LAN), ideal para pátios com conectividade limitada.
  • ✓
    Zero-fricção de adoção — sem cadastro de motoristas, sem login, sem curva de aprendizado: o motorista só aperta um botão.
  • ✓
    Hardware simples — qualquer computador ou tablet com navegador funciona como terminal, painel ou tela de operador.
  • ✓
    Extensível por design — impressora térmica e áudio são módulos plugáveis, prontos para hardware real sem reescrever a aplicação.
  • ✓
    Arquitetura enxuta e auditável — código organizado em camadas, fácil de entender, testar e evoluir.

Arquitetura do Sistema

Um único processo Node.js serve a API REST, os arquivos das três interfaces e mantém conexões WebSocket abertas para difundir eventos em tempo real. Tudo roda na rede local do pátio.

As três interfaces se comunicam com o servidor via HTTP (para ações) e recebem eventos via Socket.IO (para atualizações instantâneas). Quando o operador chama uma senha, o Painel Público e o áudio disparam no mesmo instante, sem necessidade de atualizar a página.

Padrões de Projeto Aplicados

Service Layer
Toda regra de negócio isolada em services/.
Repository Pattern
Todo acesso a dados isolado, com SQL parametrizado (proteção contra SQL Injection).
Strategy Pattern
Driver de impressora e modo de áudio são estratégias intercambiáveis por configuração.
Singleton
Pool de conexões MariaDB e instância do Socket.IO são únicas e compartilhadas.
Fail-fast
O servidor testa a conexão com o banco antes de aceitar requisições.
Transações Atômicas
Operações que alteram mais de uma tabela usam transação SQL com SELECT ... FOR UPDATE.

Tecnologias

Stack Tecnológica

Construído intencionalmente sem frameworks pesados no frontend. Cada decisão técnica prioriza portabilidade, leveza e compatibilidade com hardware modesto de pátio industrial.

CamadaTecnologiaMotivo da escolha
BackendNode.js + Express 4Leve, maduro, fácil deploy em qualquer PC de pátio industrial
Banco de dadosMariaDBRelacional, transacional (ACID), gratuito, roda localmente sem internet
Driver de bancomysql2/promiseSuporte nativo a async/await e queries parametrizadas
Tempo realSocket.IO 4WebSocket com fallback automático, API simples de eventos
Validaçãoexpress-validatorValidação declarativa de payloads na camada de rotas
FrontendHTML5 + CSS3 + JS vanillaSem build step, roda em qualquer navegador — por especificação do projeto
Síntese de vozWeb Speech APIÁudio de chamada 100% local no navegador, sem internet

Por que Vanilla JS no frontend?

É uma decisão arquitetural deliberada, não uma limitação: zero build step (sem Webpack/Vite), deploy trivial (o próprio Express serve os arquivos estáticos), compatibilidade com navegadores mais antigos comuns em terminais de pátio, e manutenção de longo prazo sem depender de versões de framework.

Dependências de Produção (Backend)

PACKAGE.JSON { "cors": "^2.8.5", "dotenv": "^16.4.5", "express": "^4.19.2", "express-validator": "^7.2.0", "mysql2": "^3.11.0", "socket.io": "^4.7.5" }

Apenas seis dependências de produção, todas maduras e amplamente auditadas — isso minimiza a superfície de ataque (supply-chain) e a manutenção de longo prazo. Requisito de runtime: Node.js 18 ou superior.

Detalhamento de Cada Tela

🖥️
Terminal de Autoatendimento
Rota: /terminal · Público: o motorista, sozinho, ao chegar
  • Botão único ("Retirar Senha") minimiza erro de operação por usuários não técnicos.
  • Retorno automático à tela inicial após 6 segundos — o terminal está sempre pronto para o próximo motorista.
  • Estado de carregamento explícito (botão desabilitado, texto "Gerando senha...") evita cliques duplicados.
  • Relógio no cabeçalho, atualizado a cada 30 segundos.
🧑‍💼
Painel do Operador
Rota: /operador · Público: o funcionário responsável pelo pátio
  • Fila de espera (esquerda) — lista ao vivo de senhas aguardando, com botão de cancelar por item.
  • Esteiras (direita) — cards mostrando status Livre/Ocupada e ações contextuais: "Chamar próxima" quando livre; "Repetir chamada" e "Finalizar atendimento" quando ocupada.
  • Últimas chamadas — contexto histórico recente sem precisar de relatório completo.
  • Indicador de conexão no cabeçalho (Conectado/Desconectado) — transparência sobre o WebSocket.
📺
Painel Público
Rota: /painel · Público: todos os motoristas aguardando no pátio
  • Um cartão por esteira, com destaque visual quando há mudança recente.
  • Lista das últimas chamadas — contexto para quem perdeu o anúncio de voz.
  • Mensagem institucional configurável e nome da empresa no cabeçalho.
  • Áudio automático via Web Speech API — exige um toque inicial na tela para "desbloquear" o som (restrição de segurança dos navegadores contra autoplay).

Modelo de Dados

MariaDB com engine InnoDB (suporte transacional ACID e chaves estrangeiras), charset utf8mb4. Três tabelas centrais governam todo o sistema.

esteirasTABELA
idINT PK
nomeVARCHAR UK
statusENUMLIVRE | OCUPADA
senha_atual_idFK null
ultima_atualizacaoDATETIME
senhasTABELA
idINT PK

dataDATE

esteira_idFK null
configuracoesSINGLETON
empresaVARCHAR
audioTINYINT
volumeTINYINT

configuracoes é uma tabela singleton — existe apenas um registro (id = 1), sem relacionamento com as demais tabelas.

Integridade Garantida no Banco

SQL — CONSTRAINTS -- RN004: não pode haver duas senhas iguais no mesmo dia UNIQUE KEY uq_senhas_numero_data (numero, data) UNIQUE KEY uq_senhas_sequencial_data (sequencial, data) KEY idx_senhas_status (status) KEY idx_senhas_data (data)
🔒
Decisão de design notável: a regra RN004 não depende só da lógica da aplicação — está garantida também no nível do banco via UNIQUE KEY, formando uma segunda camada de defesa contra inconsistências.

Máquina de Estados da Senha

O ativo mais crítico do sistema — todas as regras de negócio orbitam em torno dele.

AGUARDANDO
Terminal emite senha
→
EM_ATENDIMENTO
Operador chama
→
FINALIZADA
Operador finaliza
AGUARDANDO
→
CANCELADA
Operador cancela

Nota de implementação: embora o schema contemple CHAMADA como estado intermediário, a implementação atual transiciona diretamente de AGUARDANDO para EM_ATENDIMENTO — o estado está reservado para uma futura separação (ver Roadmap).

Transações Atômicas

Toda operação que altera mais de uma tabela é protegida por transação SQL explícita via o helper withTransaction.js:

JAVASCRIPT async function withTransaction(fn) { const connection = await pool.getConnection(); try { await connection.beginTransaction(); const resultado = await fn(connection); await connection.commit(); return resultado; } catch (error) { await connection.rollback(); throw error; } finally { connection.release(); } }

Exemplo crítico: chamarSenha() usa SELECT ... FOR UPDATE para bloquear a linha da esteira durante a transação, impedindo que dois operadores (ou dois cliques simultâneos) chamem senhas diferentes para a mesma esteira ao mesmo tempo.

Domínio

Regras de Negócio

Todas as regras estão implementadas em senhaService.js, com transições de estado protegidas por transações de banco para evitar condições de corrida.

CódigoRegraOnde é garantida
RN001Existe apenas uma fila (sem categorias/prioridade no MVP)Modelagem — tabela única, sem coluna de categoria
RN002As senhas são sequenciaisColuna sequencial + busca do último número do dia
RN003A sequência reinicia diariamenteFiltro por data em toda consulta de sequencial
RN004Não pode haver duas senhas iguais no mesmo diaUNIQUE KEY no schema — dupla proteção
RN005Cada esteira atende apenas uma senha por vezesteira_id único por senha ativa
RN006Somente senhas AGUARDANDO podem ser chamadasValidação em chamarSenha() → erro 409
RN007Somente esteiras LIVRES podem receber chamadaValidação + SELECT ... FOR UPDATE
RN008Ao chamar: senha → EM_ATENDIMENTO, esteira → OCUPADATransação atômica em chamarSenha()
RN009Ao finalizar: senha → FINALIZADA, esteira → LIVRETransação atômica em finalizarAtendimento()
RN010Toda chamada gera áudioaudioService.anunciarChamada()
RN011Toda chamada atualiza o painel instantaneamenteEvento painel:atualizacao via Socket.IO
RN012O operador pode repetir a chamadarepetirChamada() — sem mudar estado
RN013O operador pode cancelar uma senha antes do atendimentocancelarSenha() — apenas em AGUARDANDO

Anatomia de uma Regra: chamarSenha()

Para ilustrar como as regras são aplicadas na prática, o trecho abaixo mostra RN006, RN007 e RN008 sendo verificadas dentro de uma única transação atômica:

JAVASCRIPT async function chamarSenha({ senhaId, esteiraId }) { return withTransaction(async (connection) => { const esteira = await esteiraRepository.buscarPorIdComLock(esteiraId, connection); if (esteira.status !== 'LIVRE') { throw new ConflictError(\`Esteira já está OCUPADA.\`); // RN007 } const senha = await senhaRepository.buscarPorId(senhaId, connection); if (senha.status !== 'AGUARDANDO') { throw new ConflictError(\`Senha não está aguardando.\`); // RN006 } // RN008 — transição atômica dos dois estados: await senhaRepository.atualizarStatus(senhaId, 'EM_ATENDIMENTO', {...}); await esteiraRepository.atualizarStatus(esteiraId, 'OCUPADA', senhaId); }); }

Fora do Escopo do MVP

Por decisão explícita de escopo: cadastro de clientes/motoristas, login/autenticação de operadores, histórico e relatórios gerenciais, dashboard administrativo, e coordenação de UX para múltiplos operadores simultâneos (a proteção técnica contra corrida já existe no banco). Detalhes no Roadmap.

WebSocket

Comunicação em Tempo Real

Conecte-se em ws://<servidor>:<porta> — o cliente Socket.IO é servido automaticamente, sem configuração adicional.

EventoQuando ocorreQuem escuta
senha:criadaNova senha emitida no TerminalOperador
senha:chamadaSenha chamada para uma esteira (inclui dados de áudio)Painel Público (dispara áudio)
senha:repetidaOperador repetiu a chamadaOperador, Painel
senha:canceladaSenha cancelada antes do atendimentoOperador
atendimento:finalizadoAtendimento concluídoOperador, Painel
esteira:liberadaEsteira voltou ao estado LIVREOperador, Painel
painel:atualizacaoQualquer mudança relevante ("guarda-chuva")Operador, Painel

Padrão: "Evento como Gatilho, REST como Fonte de Verdade"

Um detalhe de design importante: os eventos Socket.IO não carregam necessariamente todo o estado necessário para re-renderizar a tela. Em vez disso, o evento funciona como um "algo mudou, recarregue", e o cliente busca o estado atualizado via GET /api/painel. Isso simplifica o modelo mental: o servidor nunca precisa manter réplicas parciais de estado sincronizadas no payload do evento.

🔊
A exceção é o evento senha:chamada, que carrega o payload de áudio diretamente (texto, modo, volume), pois o reprodutor de áudio precisa reagir imediatamente, sem esperar uma requisição HTTP adicional.

Manual do Sistema

Manual do Usuário — Para a Empresa de Água

Esta seção não exige nenhum conhecimento técnico. Foi escrita para o dono da empresa, o gerente do pátio e o funcionário que vai operar o sistema no dia a dia.

Visão Geral em 1 Minuto

🖥️
Terminal
Onde fica: perto da entrada, ao alcance do motorista.
Para que serve: o motorista aperta um botão e retira sua senha.
🧑‍💼
Operador
Onde fica: na mesa/guarita do funcionário responsável.
Para que serve: chama, repete e finaliza atendimentos.
📺
Painel
Onde fica: TV ou monitor grande, visível de longe.
Para que serve: mostra a senha chamada e anuncia por voz.

As três telas conversam entre si automaticamente. Quando o operador chama uma senha, o painel e o som atualizam na hora, sem precisar apertar nada.

Preparando o Dia de Trabalho

  • 1
    Ligue o computador/servidor que roda o sistema.
  • 2
    Se houver o atalho "Aguafila" na área de trabalho (Windows), dê dois cliques nele — ele liga o banco de dados, o sistema, e já abre as três telas sozinho.
  • 3
    Verifique se cada tela está aberta no equipamento certo: Terminal → tablet perto da entrada; Operador → computador do funcionário; Painel → TV do pátio, em tela cheia.
  • 4
    Na primeira vez que abrir o Painel no dia, toque uma vez na tela. Isso "libera" o som do navegador — sem esse toque, o áudio das chamadas não funciona. É uma proteção do próprio navegador, não um defeito do sistema.
  • 5
    Confira, no canto superior da tela do Operador, se está escrito "Conectado" (bolinha verde). Se estiver "Desconectado", veja a tabela de solução de problemas abaixo.

Como o Motorista Retira a Senha

  • 1
    O motorista chega ao pátio e vai até a tela do Terminal.
  • 2
    Ele toca no botão grande "Retirar Senha".
  • 3
    A tela mostra o número da senha (ex.: A012) e, se a impressora estiver conectada, um comprovante é impresso automaticamente.
  • 4
    Depois de alguns segundos, a tela volta sozinha para o início, pronta para o próximo motorista.
  • 5
    O motorista guarda o comprovante, descarrega os galões e aguarda no pátio, de olho no Painel.
💡
Não é necessário nenhum cadastro, login ou informação do motorista — o processo é intencionalmente simples para não gerar filas na hora de tirar a senha.

Como o Operador Atende a Fila

Na tela do Operador, você vê duas áreas: à esquerda, a lista de senhas aguardando, na ordem de chegada; à direita, um cartão para cada esteira, mostrando se está Livre ou Ocupada.

Para chamar a próxima senha
  • Veja qual esteira está com o cartão "Livre".
  • Clique em "Chamar próxima" no cartão daquela esteira.
  • O sistema marca a senha, atualiza o Painel e toca o anúncio de voz automaticamente.
Se o motorista não ouviu
  • Clique em "Repetir chamada" no cartão da esteira.
  • O anúncio de voz toca novamente, sem alterar nada no sistema.
Quando o carregamento terminar
  • Clique em "Finalizar atendimento" no cartão daquela esteira.
  • A esteira volta a ficar "Livre" e já pode receber a próxima chamada.
Se precisar cancelar uma senha
  • Encontre a senha na lista de espera e clique em "Cancelar".
  • O sistema pede confirmação antes de cancelar.
⚠️
Só é possível cancelar senhas que ainda não foram chamadas. Uma senha já chamada só pode ser finalizada normalmente.

O que Aparece no Painel Público

O Painel, exibido na TV do pátio, mostra: um cartão para cada esteira com o número da senha sendo atendida; a lista das últimas senhas chamadas; uma mensagem de boas-vindas personalizável no rodapé; e o relógio com o nome da empresa no topo. Sempre que uma nova senha é chamada, o cartão da esteira correspondente pisca/destaca e o sistema fala em voz alta o número da senha e a esteira.

Rotina de Fechamento do Dia

O sistema não exige nenhuma ação manual de fechamento — a numeração de senhas reinicia sozinha no dia seguinte (voltando para A001), e todo o histórico do dia permanece salvo no banco de dados. Basta desligar os equipamentos normalmente ao final do expediente.

Perguntas Comuns da Equipe Operacional

Se a luz cair no meio do dia, eu perco as senhas já emitidas?
Não. Todas as senhas ficam salvas no banco de dados assim que são geradas — apenas a tela precisa ser reaberta depois que a energia/rede voltar.
Posso ter mais de duas esteiras?
Sim, o número de esteiras é configurável (cadastro atual: 2 esteiras). Para adicionar mais, é necessário suporte técnico.
O motorista pode saber sua posição na fila antes de ser chamado?
Não no MVP atual — ele só recebe o número da senha e aguarda o anúncio. Essa melhoria já está mapeada no roadmap.

Transparência Técnica

Segurança, Limitações e Considerações Operacionais

Esta seção documenta honestamente as limitações atuais do MVP — informação essencial tanto para desenvolvedores quanto para decisões de investimento/adoção.

✅ O que o MVP já garante
  • Proteção contra SQL Injection (queries parametrizadas)
  • Proteção contra condições de corrida (transações + FOR UPDATE)
  • Integridade referencial no banco (chaves estrangeiras)
  • Unicidade garantida em duas camadas (aplicação + banco)
  • Tratamento de erro consistente, sem exceções não tratadas
  • CORS configurável
❌ O que não está no MVP
  • Sem autenticação/autorização — não expor fora de rede local fechada
  • Sem HTTPS nativo — requer proxy reverso para uso fora da LAN
  • Sem rate limiting
  • Sem coordenação visual entre múltiplos operadores
  • Sem testes automatizados identificados no repositório
  • Sem telas/endpoints de histórico e relatórios

Recomendações Antes de Produção Fora de Ambiente Controlado

  • 1
    Adicionar autenticação básica (ao menos) na tela do Operador.
  • 2
    Restringir CORS_ORIGIN a valores explícitos em vez de *.
  • 3
    Colocar o servidor atrás de um proxy reverso com HTTPS, caso o acesso deixe de ser estritamente LAN.
  • 4
    Adicionar suíte de testes automatizados, priorizando senhaService.js (regras RN001–RN013).
  • 5
    Implementar rotação/backup do banco de dados MariaDB.

✅ Faça

Leitura de Negócio

Para Investidores

Resumo, em linguagem de negócio, dos principais pontos de avaliação do ativo técnico.

🎯 Mercado Endereçável

Distribuidoras de água (poços, minas d'água, revenda em galões) que atendem caminhões em pátio são um segmento tipicamente subatendido por software — a maioria opera com processos manuais ou papel. É um padrão recorrente em setores de logística/distribuição de baixo ticket médio e alta operação.

🏗️ A Arquitetura como Ativo

Baixo custo de manutenção (seis dependências de produção). Portabilidade total — roda em qualquer máquina com Node.js + MariaDB. Extensibilidade planejada desde o início (impressora e áudio já são módulos plugáveis). Caminho claro para um modelo SaaS multi-tenant sem reescrever o domínio.

RiscoSeveridadeMitigação recomendada
Ausência de autenticaçãoAlta se exposto fora de LANAdicionar auth antes de deploy fora de rede fechada

Indicadores de Maturidade de Engenharia

  • Separação de camadas rigorosa, com comentários explícitos reforçando os limites de responsabilidade.
  • Uso correto de transações e locking pessimista em pontos de concorrência real — detalhe frequentemente negligenciado em MVPs.
  • Tratamento de erro centralizado com hierarquia de exceções de domínio.
  • Design de UX já considera cenários de falha (impressora offline, WebSocket desconectado, bloqueio de autoplay) — sinal de time pensando em produção real.

FAQ — Perguntas Frequentes

O sistema funciona sem internet?
Sim. Todo o backend, banco de dados e comunicação em tempo real rodam na rede local. A única dependência externa opcional são fontes web (Google Fonts), que podem ser removidas para operação 100% offline.
Preciso de um servidor dedicado?
Não necessariamente — qualquer computador com Node.js e MariaDB instalados, ligado à rede local do pátio, é suficiente para o volume operacional de um MVP.
Dá para usar tablets em vez de computadores?
Sim, desde que o tablet tenha um navegador moderno e acesso à rede local. O Terminal e o Painel foram desenhados pensando em telas de toque/kiosk.
O que acontece se duas pessoas tentarem chamar a mesma esteira ao mesmo tempo?
O sistema usa bloqueio de banco de dados (SELECT ... FOR UPDATE) para garantir que apenas uma das duas operações seja bem-sucedida; a outra recebe um erro claro de conflito (RN007).
Como trocar a impressora térmica?
Implementando um novo driver que siga o contrato de PrinterDriver.js e apontando a variável PRINTER_DRIVER para ele — nenhuma outra parte do sistema precisa mudar.
O sistema guarda dados de motoristas?
Não no MVP atual — nenhum dado pessoal é coletado. A senha é um número anônimo vinculado apenas a horários e status.
